I Built an AI Journal That Reflects With You

How I used Google AI Studio, Gemini, Firebase, Google Maps, and Cloud Run to turn a starter lab into a secure, location-aware reflection companion designed to fail gracefully.

Gemini Journal & Reflections12 min readEngineering · Product · AI
In this article The product idea How AI Studio shaped it Implementation steps Beyond the starter lab Four-part evaluation What I learned

Most journal apps are excellent at remembering what you wrote. They are much less useful when you need help understanding it.

That gap became the starting point for Gemini Journal & Reflections: a private web app where a journal entry becomes an ongoing conversation. A user can explore an experience through deep reflection, compress it into an executive summary, or turn it into a brainstorming session—all without moving their writing between different tools.

The real challenge was not connecting a text box to an AI model.

It was building the product around the model: identity, multi-turn memory, private persistence, useful failure states, location context, role-based controls, and a deployment path that does not put secrets in the browser.

I used Google AI Studio as my agentic development workbench to move from product intent to a working Next.js architecture. I used it to decompose requirements, generate and refine TypeScript components, reason about integration failures, and convert security expectations into durable project rules. Gemini then became part of the application itself through the server-side Google Gen AI SDK.

The product idea: one thought, three useful perspectives

Journaling is rarely a one-shot prompt. A thought develops as we revisit it, question it, and connect it to earlier context. I therefore designed the core interaction as a conversation rather than a single generation request.

Lens 01

Deep Reflection

Responds with empathy, perspective, and a gentle follow-up question.

Lens 02

Key Summary

Extracts themes, emotions, and actionable takeaways.

Lens 03

Brainstorm

Generates multiple angles, possible solutions, and prompts for exploration.

Shared memory

Multi-turn context

Keeps earlier messages in the conversation so a thought can develop naturally.

The selected lens changes the server-side system guidance, while prior messages are sent as structured conversation history. These are not three cosmetic buttons over the same prompt: each mode changes the task Gemini is asked to perform.

The first message becomes an automatic title, the AI response becomes a short preview, and the full exchange is saved as one evolving Firestore document. This makes history searchable and lets a user resume a thought instead of starting from zero.

How Google AI Studio shaped the build

1. Turning a broad idea into modules

I began with the experience—private reflection with useful AI assistance—and decomposed it into clear boundaries:

Next.js client
  ├── Firebase Authentication
  ├── Reflection workspace
  ├── Searchable history
  ├── Location picker
  └── Admin and notification interfaces

Next.js server routes
  ├── /api/gemini/reflect
  └── /api/notifications/*

Managed services
  ├── Gemini models
  ├── Cloud Firestore
  └── Google Cloud Run

This prevented the Gemini key from drifting into a client component and gave each integration a specific responsibility.

2. Developing persistent engineering guardrails

I translated security requirements into repository-level directives in AGENTS.md and GEMINI.md. They cover key isolation, owner-bound Firestore paths, modern Google Maps APIs, admin-role protection, append-only audit records, webhook validation, and four-second outbound timeouts.

This was one of the most valuable uses of AI Studio: not merely asking it to generate a feature, but giving it constraints that remained visible while the feature evolved.

3. Iterating through real integration failures

The app needed to behave well in both configured Cloud environments and fast preview environments. AI Studio helped work through cases such as an unauthorized Firebase Auth domain, a missing or invalid Maps key, a blocked sign-in popup, a stale JavaScript chunk after deployment, and competing Next.js build artifacts.

Those cases became visible product states: copyable domain setup guidance, anonymous sandbox access, an interactive map fallback, an application error boundary, and separate .next-dev and .next build directories.

4. Building verification into the workflow

I added Vitest coverage for request validation, mode selection, multi-turn construction, the model fallback ladder, Firestore path construction, payload cleaning, persistence, and deletion. Security checks and unit tests also run before the Cloud Run deployment job in GitHub Actions.

AI Studio accelerated implementation, but the repository—not the chat transcript—is the source of truth. That distinction matters whenever an AI-assisted build is evaluated for authenticity.

Implementation, step by step

Step 1: Create the application shell

I built the interface with Next.js 15 App Router, React 19, TypeScript, Tailwind CSS, Motion, and Lucide icons. The signed-in experience is divided into a responsive history sidebar, a central reflection workspace, and an admin view offered only to authorized users.

The workspace includes meaningful async states instead of dead clicks: authentication loading, AI generation, Firestore saving, successful persistence, sync failure, notification delivery, geolocation lookup, and map configuration notices.

Step 2: Add Google single sign-on and demo access

Firebase Authentication handles Google sign-in, so the application never stores or processes a password. An auth-state listener restores the session and then synchronizes the user profile in Firestore.

  • When Firebase reports auth/unauthorized-domain, the UI shows the current hostname, explains where to authorize it, and provides a copy button.
  • When popup authentication is inconvenient in a sandbox or embedded preview, anonymous Firebase Authentication provides a zero-popup demo path.

This preserves the real SSO experience while making the project immediately testable during a demo.

Step 3: Put Gemini behind a server route

The client sends journal text to /api/gemini/reflect; only that server route imports @google/genai and reads GEMINI_API_KEY.

Before invoking Gemini, the route rejects malformed JSON, empty prompts, and prompts over 12,000 characters. It wraps the current entry in explicit <user_journal_content> boundaries and instructs the model to treat that content as journal material—not as permission to change its identity, reveal instructions, or execute commands.

The route also builds conversation history using Gemini's user and model roles. This is what makes follow-up reflection possible.

for (const model of MODEL_FALLBACK_LADDER) {
  try {
    const response = await ai.models.generateContent({
      model,
      contents,
      config: { systemInstruction, temperature: 0.7 }
    });

    if (response.text?.trim()) {
      return { text: response.text, modelUsed: model };
    }
  } catch (error) {
    if (!isRecoverable(error)) throw error;
  }
}

The configured ladder tries gemini-3.6-flash, gemini-3.1-flash-lite, gemini-flash-latest, and gemini-3.7-flash for recoverable availability, quota, and model-not-found failures. Non-recoverable errors fail fast instead of wasting additional requests.

Step 4: Save only after the complete interaction succeeds

Each journal document lives at:

/users/{userId}/interactions/{interactionId}

It contains ordered user/model messages, title, mode, summary, timestamps, optional location, sentiment, and the model that produced the response.

A small but important usability decision protects unfinished writing: the composer clears only after Gemini returns and Firestore confirms the write. If either stage fails, the original text remains in the input and the UI explains that it can be retried.

Before persistence, a payload utility normalizes undefined values so Firestore does not reject an otherwise valid interaction. A real-time onSnapshot subscription keeps history synchronized and sorted by its latest update.

Step 5: Make place part of the memory

Location is often part of why a memory matters, so an entry can include a place name and coordinates.

With a valid NEXT_PUBLIC_GOOGLE_MAPS_API_KEY, the picker loads the Maps JavaScript API and uses the modern AdvancedMarkerElement. Map clicks create or move the pin, preset cities are available, and browser geolocation can attach the user's current coordinates. The integration also includes the required attribution ID gmp_mcp_codeassist_v1_aistudio.

The distinctive part is the dual-mode design. If no key is configured, the key has the wrong format, authentication fails, or the Maps library cannot load, the location feature does not disappear. It switches to a clearly labeled interactive vector canvas with clickable coordinate estimation, city presets, and GPS support.

That fallback is deliberately presented as a prototype approximation—not as live reverse geocoding. It keeps the flow demonstrable without pretending simulated data came from Google Maps.

Step 6: Add external notifications without coupling them to saving

Users can format a reflection notification for Slack or Discord, or preview a simulated email alert. The client does not call those third-party services directly. It sends a request to a Next.js server route, where the target is checked before any outbound request occurs.

The current safeguards require HTTPS, reject obvious loopback, private, and metadata addresses, constrain Slack and Discord destinations by hostname, and cancel delivery after four seconds with AbortController.

Most importantly, notification delivery is separate from journal persistence. A webhook timeout or third-party outage can fail the alert, but it cannot roll back or erase the reflection.

Step 7: Add role-aware administration and an immutable ledger

The project includes an admin console with live user counts, role management, security information, and recent audit activity. Admin navigation is hidden for ordinary users, while Firestore rules remain the authoritative boundary for data reads and writes.

Standard users may update their own profile only when the role field remains unchanged. Administrators can manage roles and inspect users. Audit records can be created but never updated or deleted, producing an append-only history of administrative activity.

Conditional UI is convenience, not authorization. The meaningful controls live in Firestore rules through authenticated-owner and admin checks.

Step 8: Prepare a repeatable Cloud Run release

The production configuration uses Next.js standalone output and a multi-stage Node 22 Alpine container. The final image runs as a non-root nextjs user and contains only the standalone server, static output, and public assets.

GitHub Actions gates deployment on the security script and unit tests, then builds the container, pushes it to Artifact Registry, and deploys it to Cloud Run with GEMINI_API_KEY mounted from Secret Manager. A parallel cloudbuild.yaml path is also included for Google Cloud Build.

This architecture supports managed restarts and scaling, but I do not equate an infrastructure choice with measured uptime. Real uptime claims require production monitoring, availability data, and alert history.

What is genuinely beyond the starter lab?

The repository history makes the progression clear. After the initial scaffold, the project added more than 2,000 lines across Maps, notification, RBAC, audit, error-state, and security modules, followed by map/auth stabilization and automated tests.

  • A multi-turn journal rather than a one-shot prompt demo.
  • Three task-specific Gemini lenses in one persistent conversation.
  • Automatic model failover with fail-fast handling for non-recoverable errors.
  • Location-grounded entries with modern Google Maps markers and a usable no-key fallback.
  • Searchable, filterable, real-time Firestore history.
  • Server-mediated Slack and Discord notifications isolated from saving.
  • Admin role management and append-only audit records.
  • Failure-aware UX for auth domains, blocked popups, stale chunks, Maps configuration, generation, and Firestore errors.
  • Automated tests, secret scanning, containerization, and deployment gates.
The difference: this is not merely “Gemini can respond to text.” It is “a person can trust the surrounding workflow enough to use it.”

Evaluating the build against the four criteria

Authenticity

The product has its own interaction model, visual language, data model, location experience, admin surface, and notification workflow. Its unique value sits in how those pieces work together around reflection.

Usability

Google SSO removes password friction. Sandbox access, real-time history, starter prompts, keyboard submission, retained text after failure, search, status feedback, and responsive navigation keep the journey coherent.

Stability

Bounded inputs, model fallback, graceful Maps degradation, preserved drafts, an error boundary, isolated build directories, request timeouts, a standalone container, and test-gated deployment reduce common failure modes.

Security

Owner-scoped database paths, role-change restrictions, immutable audit records, server-only Gemini credentials, input limits, prompt-content boundaries, non-root containers, and initial SSRF controls establish a meaningful baseline.

The security script's blocked result is important context. In this environment its child-process Git scan falls back to inspecting ignored local files, and it also flags a prohibited variable name mentioned in developer documentation. No secret value was printed during review, but the scanner behavior and documentation finding should be corrected before describing the gate as green.

The next security-hardening steps

The Gemini and notification API routes should verify Firebase ID tokens rather than trusting that only the authenticated UI will call them. Webhook validation should use exact host and path allowlists plus DNS resolution checks to resist suffix tricks and DNS rebinding. The notification payload should be runtime-validated against one shared schema. Finally, audit-log creation rules should require an admin identity and validate every required field instead of allowing any authenticated user to append arbitrary records.

Calling these out does not weaken the project story. It demonstrates that security is a continuously verified property, not a badge added to a README.

What I learned

The biggest lesson from building Gemini Journal & Reflections is that the AI response is only one part of an AI product.

A useful system also needs to know who the user is, protect where their data lives, preserve work when dependencies fail, explain configuration problems, and make infrastructure degradation visible without destroying the experience.

Google AI Studio helped me move quickly from intent to implementation and reason across the full stack. The best results came when I treated it as a collaborative engineering environment: define boundaries, make constraints persistent, inspect the generated code, reproduce failures, and verify final behavior with tests and builds.

The outcome is more than a journal with an AI button. It is a reflection workspace that can hold a conversation, remember context, attach a place, survive several common failures, and expose its own security posture honestly.

That is the kind of AI application I want to keep building: thoughtful in the interface, ambitious in its features, and disciplined about the systems underneath.
